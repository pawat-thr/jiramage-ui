## 🐞 Spec-link cache bug (teammate couldn't map specs after pulling)

- Root cause: the spec-link localStorage cache (`jiramage-spec-links-*`) persisted
  results **even when the fetch had failed**, and survived version upgrades — so a
  bad/empty cache from an old build suppressed Spec chips for up to 24h after pulling a fix
- Fixed: the cache key is now **version-stamped** (any new build starts clean and
  deletes old-version caches), and **failed fetches are never persisted** (they retry next session)
- Teammates on old builds: pulling this version self-heals — no manual localStorage clearing needed

## 🔥 Burn tracking on Team Task

- Cards in **In Dev / In Dev Testing** (configurable: `BURN_STATUSES` env) show a **burn meter**
  under the status (Jira time-tracking style): a mini progress bar + `12.4 / 16 pt` — burned points since first entering dev vs the estimate (1 manday = 8 points); **blue** on track, **amber** at ≥75%, **red** when over
- Manday math: Mon–Fri only, **09:30–12:00 + 13:00–18:30** (= 8 working hours, lunch excluded); weekends excluded. Hardcoded for this beta — a Settings work-time option is planned
- Dev-start comes from the issue **changelog** (first transition into a burn status), cached in
  localStorage (immutable per issue+status); chip turns **red when burn exceeds the estimate**
- Cards not in those statuses show nothing (as specified); 9 new unit tests for the working-time math (134 total)
- New env: `BURN_STATUSES=In Dev,In Dev Testing`

## 📊 Burn UX round 2

- Burn moved from under the status pill into its **own "Burn" column** on Team Task (My Tasks unchanged) — meters align down the column; non-dev rows show a dash
- Meter is a Jira-time-tracking-style widget: `12.0 / 16 pt` + staged progress bar (**blue** on track, **amber** ≥75%, **red** over) — no emoji
- **Unestimated subtasks are now visible**: subtask rows without story points show an amber **"no estimate"** badge in the Burn column; in-dev cards without points show `X pt · no estimate` in amber
- **Dashboard "Active subtasks · points"**: each member with in-dev cards gets a second thin bar — **dev burn vs estimated points** (sum of burned points ÷ sum of estimates on their in-dev cards, 1 manday = 8 pt), same blue/amber/red staging, with a `burn X / Y` label

## 🔁 Burn round 3: intervals + finished stats

- **Burn is now interval-based**: leaving In Dev pauses the clock, coming back continues it — the meter sums every period the card actually spent in a burn status (from the full status changelog), instead of counting straight through from the first entry
- **Post-dev cards show a frozen "used" stat**: cards in `BURN_FINISHED_STATUSES` (env, default PR Review / Waiting for deployment / Done) display `used X / Y pt` — green when finished within estimate, red when it went over; muted bar, clearly not live
- Cards that never entered a burn status show nothing (dash), so old pre-workflow cards stay clean
- Performance: changelogs fetch only for visible rows (Active-only hides most Done cards); first full "Showing all" load on a 340-row table takes ~20s of background fetching, then the interval cache (localStorage, keyed per issue+status) makes revisits ~4s
- Dashboard burn bars unchanged — they track live in-dev burn only

## 🔵 QA Mode sub-site (init)

- **New sub-site at `/jiramage/qa`** (pages will live at `/jiramage/qa/<page>`): same shell and theme as the main site with the **accent swapped red → blue** and the brand reading **QA-mage.**
- Entered via a **"QA Mode" button** in the main top bar (before the notification bell); "← Main" in the QA top bar goes back — the blue accent applies only while inside
- First page: a **Dashboard identical to the main home page but fed by the QA team's issues** — new env `QA_EMAILS` (comma-separated QA emails; empty shows a setup hint). Member charts, subtask points, and burn bars all seed from the QA list
- **Team Task page inside QA Mode** — the full main-site page (member/type/status filters, search, spec chips, ⚡ prompt, burn column, move/reassign) fed by the QA team; dashboard member click drills into it with the filter set. No Settings in QA Mode — the main site's Settings applies everywhere
- **QA burn**: QA Mode's burn meters key off the **`In Progress`** status (env `QA_BURN_STATUSES`) instead of In Dev — same interval logic, same Mon–Fri 9:30–12:00 + 13:00–18:30 working-time rules, same finished-status handling. The burn machinery is now status-set parameterized, with per-set caching
- Unknown `/jiramage/qa/*` paths redirect to the QA dashboard
- **Proxy fix found during verification**: the dev proxy matched the `/jira` prefix, so `/jiramage/*` URLs were being forwarded to Atlassian (full-page loads showed Jira's 404) — the proxy is now anchored to `^/jira/` exactly

## 🔵 QA burn: finished stats + performance

- New env **`QA_BURN_FINISHED_STATUSES=Done`** — QA cards that reach Done show the frozen **`used X / Y pt`** stat (green within estimate / red over), exactly like the main site's finished handling; the finished-status set is parameterized per mode like the burn set
- **Performance strategy for big histories** (the QA team has ~3,000 issues):
  - finished stats fetch **only for subtasks** (bug/incident tickets are never burn-tracked)
  - at most **150 uncached changelog fetches per view**, newest cards first
  - meters render **progressively per batch** (cached ones instantly) instead of after the whole sweep — first stats appear within ~5s on a 2,900-row table

## 📅 QA Capacity Planner (QA Mode)

New page `/jiramage/qa/capacity` — a real monthly planning tool for the QA team.

- **Calendar**: current month by default (‹ › navigation + Today), one row per QA (`QA_EMAILS`), one column per day; weekends dimmed (0 capacity), today highlighted; sticky QA column with monthly planned/capacity totals
- **Model**: 1 point = 1 hour; default 8 pt per working day; per-day capacity overrides via click (Leave 0 / Half 4 / Full 8 / custom) for holidays & partial days
- **Planning**: unplanned Jira tasks (pointed, not done) in a collapsible backlog — ⚡ auto-plan fills free capacity day by day (20 pt → 8/8/4, next task starts in the same day's remainder), or **drag a task onto any QA's day** (drag to another QA = reassign in the plan)
- **Chunks** are draggable between days/QAs and click-editable (points, remove, open in Jira)
- **Delays**: set a chunk's ACTUAL points and hit **Save + Reflow** — the actual stays pinned (day shows overloaded red, e.g. 12/8), everything after re-lays into the next free capacity and moved work is marked **⚠ delayed**; per-row ↻ reflow re-lays from today
- **States**: planned (neutral) / in progress (blue) / done (green) / delayed (amber ⚠) / overloaded day (red footer); every chunk keeps its Jira key with an open-in-Jira link
- **Persistence**: Firestore collection `qaPlan`, one doc per QA per month; v1 keeps plans within the visible month (spill reports "didn't fit this month")
- Verified live: the spec's exact example (8/8/4 split, second task filling the remainder, delay push with ⚠ marking)
- **UX round 2**: backlog is now **grouped per QA member** (avatar header, task/pt totals, "⚡ plan all", scrollable) — no more one giant chip soup; new **member filter** (narrows backlog AND calendar rows to one QA) and **task search**; drag-drop verified end-to-end (place / move between days / reassign across QAs)
- **Bug fixed**: a broken guard made calendar drops only register on weekend cells — dragging tasks onto weekdays silently did nothing; drops now work on every day, with proper dataTransfer wiring for cross-browser dragging
- **UX round 3 — layout pivot (task-first)**: rows are now the **tasks, grouped by parent story**, not the QAs
  - frozen left column = the task card: color stripe, key (Jira link), name, `planned/total pt` (red when over-allocated), owner QA avatars, done ✓; story header rows in violet above their tasks
  - **capacity strip** on top: one compact row per QA (avatar, monthly planned/capacity, ↻ reflow); day cells show `planned/cap` (red when overloaded, just the capacity when empty) — click to set Leave/Half/Full, **drop an unplanned task on a cell to plan it for that QA from that day**; collapsible to only-QAs-with-a-plan via the header toggle
  - calendar cells show each task's chunks with points + the QA's name; chunks drag along their own row to move days, hover ✕ removes, click opens the editor — which now also has **"Move this chunk to \[QA\]"** for reassignment
  - **unplanned dock frozen at the bottom** (sticky, collapsible): all unplanned tasks as chips (key, name, remaining pt, QA avatar, ⚡ auto-plan) — drag a chip onto a capacity cell to schedule it
  - member filter + search now drive all three zones (strip, task rows, dock)
- e2e smoke maintenance: the my-tasks/team-task check now accepts a rendered empty state (data-dependent — zero active tasks assigned is not a failure)
- **UX round 4 — readability + dock overhaul** (feedback: "display so small", "unplan is very hard to pick 1 item")
  - everything sized up: day columns 76→92px, chunk points 11→13px with 10px QA names, task cards 280px wide with 13px key/name, capacity cells 10→12px, larger avatars and day headers
  - the unplanned dock is no longer one chip soup: it's a taller scrollable drawer (45vh) with each task a full row (key · name · remaining pt · QA avatar · ⚡) in an aligned grid
  - dock grouping is **story-first** (feedback: "when i plan user A do subtask a,b,c from story a i dont know what card is from what story"): violet story headers matching the main table, subtasks listed under their story with per-row QA avatars, and a per-story **"⚡ Plan all"** that schedules every subtask for its own QA in one click (skips + reports subtasks without a QA assignee); subtasks with a non-QA assignee show a "no QA" tag — drop those on a capacity row to pick who

## 📅 Capacity Planner in MAIN mode too

The planner is no longer QA-only: main mode gets **Capacity Planner (beta)** at
`/capacity` (nav after Spec Wizard), planning for the dev team (you +
`TEAM_EMAILS`) with the team's own Jira issues. Same page component powers both
modes — emails, issue fetcher, and labels are props (QA texts become
"member"/"assignee" in main mode). Plans share the `qaPlan` collection; docs are
keyed per email + month, so the two modes can't collide (and a person in both
teams correctly sees one shared plan).

### Planner bug fixes (both modes)

- **Stories no longer leak into the unplanned dock**: the planner only handles
  SUBTASKS now (issues with a parent) — pointed stories used to appear as their
  own one-row "group" and, being unassigned/PM-assigned, showed the confusing
  "no QA" tag. Story names still show in group headers (read from each
  subtask's parent field).
- **Hidden-email assignees map correctly**: Atlassian privacy settings can hide
  a user's `emailAddress` in API responses even though JQL matched it — those
  subtasks wrongly showed as "no assignee". Fixed with an accountId→email
  fallback via `resolveAccountIds` (cached, one lookup per configured member).

### Grooming flow: unassigned subtasks (both modes)

Pain point: after SA grooming, subtasks exist with NO assignee — invisible to
every assignee-filtered fetch, so the team couldn't see them to assign by
effort. Now:

- the planner also fetches **unassigned issues** (`assignee is EMPTY`, same
  projects/window) and shows those subtasks in the dock under their stories
  with an amber **`unassigned`** tag
- an amber **"unassigned (n)"** toggle in the dock header shows/hides them
  (the fetch is project-wide, so other squads' unassigned subtasks appear too);
  **hidden by default** — open it when grooming
- the toolbar search now also matches the **story** a subtask is grouped by
  (story key or story name), across the calendar rows and the dock
- new **Release filter** in the planner toolbar (both modes): filters calendar
  rows and the dock by the RELEASE tagged on each subtask's parent story
  (options come from the stories the team's tasks actually belong to)
- **assign by effort = one drop**: dropping an unassigned subtask on a member's
  capacity row **sets the Jira assignee AND plans it** from that day (toast
  confirms "· assigned in Jira"; if the Jira write fails the plan still saves
  and the toast says so)

## 📜 Long task lists tamed (Team Task / My Tasks, both modes)

Issue tables no longer render every row: each type group shows **50 rows with
"Show 50 more" / "Show all"** and its header row is **click-to-collapse** (▾/▸).
A QA-mode "Showing all" view of ~2,900 issues went from a ~110,000px endless
scroll to ~260 rendered rows (about 10× shorter, and much smoother) — filters,
search, and the issue counter still work on the full set.

New `qaPlan/{docId}` block: any signed-in member can read/write the QA plans.
