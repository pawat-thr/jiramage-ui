# v0.1.8 (beta) — What's new since v0.1.7

> beta.1 in progress. Pre-release builds show the git hash again (`v0.1.8-beta.1+<hash>`).

## 🐞 Spec-link cache bug (teammate couldn't map specs after pulling)

- Root cause: the spec-link localStorage cache (`jiramage-spec-links-*`) persisted
  results **even when the fetch had failed**, and survived version upgrades — so a
  bad/empty cache from an old build suppressed Spec chips for up to 24h after pulling a fix
- Fixed: the cache key is now **version-stamped** (any new build starts clean and
  deletes old-version caches), and **failed fetches are never persisted** (they retry next session)
- Teammates on old builds: pulling this version self-heals — no manual localStorage clearing needed

## 🔥 Burn tracking on Team Task

- Cards in **In Dev / In Dev Testing** (configurable: `BURN_STATUSES` env) show a **burn meter**
  under the status (Jira time-tracking style): a mini progress bar + `12.4 / 16 pt` — burned points since first entering dev vs the estimate (1 manday = 8 points); **blue** on track, **amber** at ≥75%, **red** when over
- Manday math: Mon–Fri only, **09:30–12:00 + 13:00–18:30** (= 8 working hours, lunch excluded); weekends excluded. Hardcoded for this beta — a Settings work-time option is planned
- Dev-start comes from the issue **changelog** (first transition into a burn status), cached in
  localStorage (immutable per issue+status); chip turns **red when burn exceeds the estimate**
- Cards not in those statuses show nothing (as specified); 9 new unit tests for the working-time math (134 total)
- New env: `BURN_STATUSES=In Dev,In Dev Testing`

## 📊 Burn UX round 2

- Burn moved from under the status pill into its **own "Burn" column** on Team Task (My Tasks unchanged) — meters align down the column; non-dev rows show a dash
- Meter is a Jira-time-tracking-style widget: `12.0 / 16 pt` + staged progress bar (**blue** on track, **amber** ≥75%, **red** over) — no emoji
- **Unestimated subtasks are now visible**: subtask rows without story points show an amber **"no estimate"** badge in the Burn column; in-dev cards without points show `X pt · no estimate` in amber
- **Dashboard "Active subtasks · points"**: each member with in-dev cards gets a second thin bar — **dev burn vs estimated points** (sum of burned points ÷ sum of estimates on their in-dev cards, 1 manday = 8 pt), same blue/amber/red staging, with a `burn X / Y` label

## 🔁 Burn round 3: intervals + finished stats

- **Burn is now interval-based**: leaving In Dev pauses the clock, coming back continues it — the meter sums every period the card actually spent in a burn status (from the full status changelog), instead of counting straight through from the first entry
- **Post-dev cards show a frozen "used" stat**: cards in `BURN_FINISHED_STATUSES` (env, default PR Review / Waiting for deployment / Done) display `used X / Y pt` — green when finished within estimate, red when it went over; muted bar, clearly not live
- Cards that never entered a burn status show nothing (dash), so old pre-workflow cards stay clean
- Performance: changelogs fetch only for visible rows (Active-only hides most Done cards); first full "Showing all" load on a 340-row table takes ~20s of background fetching, then the interval cache (localStorage, keyed per issue+status) makes revisits ~4s
- Dashboard burn bars unchanged — they track live in-dev burn only

## 🔵 QA Mode sub-site (init)

- **New sub-site at `/jiramage/qa`** (pages will live at `/jiramage/qa/<page>`): same shell and theme as the main site with the **accent swapped red → blue** and the brand reading **QA-mage.**
- Entered via a **"QA Mode" button** in the main top bar (before the notification bell); "← Main" in the QA top bar goes back — the blue accent applies only while inside
- First page: a **Dashboard identical to the main home page but fed by the QA team's issues** — new env `QA_EMAILS` (comma-separated QA emails; empty shows a setup hint). Member charts, subtask points, and burn bars all seed from the QA list
- **Team Task page inside QA Mode** — the full main-site page (member/type/status filters, search, spec chips, ⚡ prompt, burn column, move/reassign) fed by the QA team; dashboard member click drills into it with the filter set. No Settings in QA Mode — the main site's Settings applies everywhere
- **QA burn**: QA Mode's burn meters key off the **`In Progress`** status (env `QA_BURN_STATUSES`) instead of In Dev — same interval logic, same Mon–Fri 9:30–12:00 + 13:00–18:30 working-time rules, same finished-status handling. The burn machinery is now status-set parameterized, with per-set caching
- Unknown `/jiramage/qa/*` paths redirect to the QA dashboard
- **Proxy fix found during verification**: the dev proxy matched the `/jira` prefix, so `/jiramage/*` URLs were being forwarded to Atlassian (full-page loads showed Jira's 404) — the proxy is now anchored to `^/jira/` exactly

## 🔵 QA burn: finished stats + performance

- New env **`QA_BURN_FINISHED_STATUSES=Done`** — QA cards that reach Done show the frozen **`used X / Y pt`** stat (green within estimate / red over), exactly like the main site's finished handling; the finished-status set is parameterized per mode like the burn set
- **Performance strategy for big histories** (the QA team has ~3,000 issues):
  - finished stats fetch **only for subtasks** (bug/incident tickets are never burn-tracked)
  - at most **150 uncached changelog fetches per view**, newest cards first
  - meters render **progressively per batch** (cached ones instantly) instead of after the whole sweep — first stats appear within ~5s on a 2,900-row table
